# 나의 오렌지 나무 (성장 시각화)

> 상태: **구현 중**. 2026-08-29에 보류를 풀었다.
> 보류했던 이유와 그걸 어떻게 풀었는지를 남긴다 — 나중에 "왜 이런 규칙인가"를 다시 묻지 않기 위해서다.

## 축을 둘로 갈랐다

보류의 원인은 성장의 축을 하나로 둘지 둘로 둘지 정하지 못한 것이었다. 결론은 **둘로 가른다**.

| 축 | 무엇이 정하나 | 사용자가 통제하나 |
|---|---|---|
| **나무** | 내 누적 기록일 수 | O |
| **열매** | 비트코인 가격 | X |

이렇게 가르면 "가격 연동"의 가장 큰 위험이 사라진다. 매일 기록했는데 하락장이라
나무가 죽어가면 사용자는 앱을 끈다. 나무를 내 기록에만 묶어두면 **하락장에도 나무는
절대 작아지지 않는다**. 가격은 열매의 개수와 크기만 흔든다.

> 규칙으로 못박은 것: 하락장에서도 열매는 최소 1개다. 0개가 되면 "벌 받는" 화면이 되고,
> 그건 나무를 시들게 하는 것과 같은 실수다.

## 나무 — 누적 기록일 수

| 단계 | 조건 | 뜻 |
|------|------|-----|
| 씨앗 | 0일 | 첫 기록을 기다림 |
| 새싹 | 1~6일 | 첫 주를 넘기는 구간 |
| 어린나무 | 7~29일 | 습관이 붙기 시작 |
| 나무 | 30~99일 | 한 달을 넘긴 기록 |
| 큰나무 | 100일~ | |

판정에 쓰는 값은 이미 있던 것이다 — `GET /history` 응답의 `total_days`(기록이 있는
날짜의 개수). 새 집계 로직을 만들지 않았다.

## 열매 — 비트코인 가격

기준선은 **그 사용자가 기록한 날들의 가격 평균**이다. 시장 전체의 등락이 아니라
"내가 기록해온 구간 대비 지금"을 본다.

- `change_pct = (현재가 - 기준선) / 기준선 × 100`
- 개수: `< -20%` → 1 / `-20~0%` → 2 / `0~20%` → 3 / `20~50%` → 5 / `50%~` → 7
- 크기: `< 0%` → small / `0~30%` → medium / `30%~` → large

이게 성립하려면 **기록 시점의 가격을 박제**해야 한다. `posts.btc_price_krw` 컬럼에
게시물 생성 시점의 가격을 넣는다. 부수 효과로 게시물 하나하나가 "그날 1 BTC = 얼마"의
기록이 된다 — DCA 하는 사용자에게는 이쪽이 나무보다 더 쓸모 있을 수 있다.

기존 게시물은 `NULL`이다. 과거 가격을 알 수 없어 백필하지 않았다.

### 박제 지점이 세 곳이다 (주의)

`Post(...)`를 만드는 곳이 셋이고, **세 곳 모두에 가격을 넣어야 한다.** 한 곳만 빠뜨리면
그 경로로 올린 게시물만 조용히 `NULL`이 되고, 기준선이 틀어지는데 에러는 안 난다.

| 위치 | 경로 |
|---|---|
| `backend/app/routes/videos.py` | `POST /videos/confirm` — 단일 동기 업로드(레거시) |
| `worker/tasks/full_pipeline.py` | 단일 영상 파이프라인 |
| `worker/tasks/full_pipeline_multi.py` | 다중 미디어 파이프라인 — **실사용 대부분이 이쪽** |

worker 두 곳은 `full_pipeline._current_btc_price_krw()` 하나를 같이 쓴다. worker가
backend 모듈을 부를 수 있는 것은 `worker/config.py`가 backend 경로를 `sys.path`에
넣어주기 때문이다(`app.models.post`를 이미 그렇게 쓰고 있다). worker venv에도
`httpx`·`redis`가 이미 있어 새 의존성은 없다.

## 가격을 못 가져올 때

이 서비스에 시세를 가져오는 경로가 없었기 때문에 외부 의존성(CoinGecko)이 새로 생겼다.
그래서 실패를 정상 경로로 취급한다.

- **캐시는 두 겹이다.** 프로세스 로컬 인메모리가 1차, Redis가 2차. 조회 순서는
  인메모리(신선 5분) → Redis(신선 5분) → CoinGecko → 인메모리(stale 24시간) →
  Redis(stale 24시간) → None.

  Redis만 두면 안 되는 이유는 실측으로 확인했다. `REDIS_URL`이 없는 환경에서는 캐시가
  통째로 사라져 프로필을 열 때마다 CoinGecko를 직접 때렸고, 몇 번 만에 **429 Too Many
  Requests**를 맞아 모든 사용자의 열매가 사라졌다. 운영에서도 Redis가 죽으면 같은 상태로
  조용히 떨어진다. 인메모리 계층을 넣은 뒤 10회 요청 → 외부 호출 1회로 줄었다.
- **실패 백오프 60초.** 외부 조회가 실패하면 그 시간 동안은 재시도하지 않고 곧장
  stale/None으로 간다. 이게 없으면 429를 맞은 뒤에도 요청마다 계속 두들겨 차단이 안 풀린다.
- 그마저 없으면 응답의 `fruit.available: false`. 화면은 **나무만 그리고 열매 UI를 조용히
  숨긴다**. 에러를 크게 띄우지 않는다 — 사용자 잘못이 아니고, 나무는 여전히 유효하다.
- 가격 조회가 업로드를 막지 않는다. 실패하면 `btc_price_krw`를 `NULL`로 두고 게시물은
  정상 생성된다.
